# PhysiGuard deployment-readiness review

**Status: research prototype; not ready to connect to or control a vehicle.** This review distinguishes passing software checks from evidence that still requires physical cells, a target BMS, and an authorized safety program.

## Verified in the current source tree

- Backend full test suite, Ruff lint, and strict mypy pass. API health and creation checks now require a readable detection calibration with matching configuration hash and calibration metadata. Missing calibration degrades health and blocks new sessions with HTTP 503; missing benchmark artifacts return a clear 404. Regression tests cover both failure cases.
- Primary `static-website/` installs from a clean source copy with `npm ci`; all 26 tests, TypeScript, build, and `npm audit` pass. The backend serves the built site and its health, scenario, benchmark, and limits endpoints return expected responses. Seven offline recordings are valid, labeled as recorded, and included in the built site.
- The frontend dependency audit reports zero vulnerabilities after upgrading the Vite/Vitest toolchain. The production build and 26 tests pass; the current chunk split is about 513 kB vendor JavaScript plus 63 kB application JavaScript (131 kB + 20 kB gzip), and Vite still emits a >500 kB advisory for the vendor chunk.
- The selected frontend's three-pass 60× soak completed all seven scenarios in each of three rounds: 21 sessions, 600 frames each, and no WebSocket error frames or malformed/missing-frame assertions. Python `tracemalloc` reported 4,456,522 bytes current growth and 10,008,749 bytes peak growth across the process. No acceptance threshold was defined, and this excludes native allocations and total process RSS, so it is evidence only—not a memory pass.
- Backend failure behavior received additional checks: the full backend suite passes 88 tests; API tests exercise missing, malformed, and metadata-incomplete `detection.yaml` files (health degrades and session creation is rejected), missing benchmark artifacts (404), and corrupt benchmark JSON (503). A real Uvicorn subprocess streamed a baseline session, then was terminated; the WebSocket closed with code 1006. This verifies disconnect detection at the protocol level, not browser reconnection, user messaging, recovery, or graceful shutdown.
- The process-stop drill is reproducible with `backend/.venv/Scripts/python.exe scripts/failure_drill.py` on Windows or `backend/.venv/bin/python scripts/failure_drill.py` on POSIX; `make failure-drill` wraps the same script when GNU Make is available. It passed twice in this workspace.
- CALCE CS2_33 experiment: 825 discharge cycles from one 1.1 Ah laboratory cell; fit on 150 earlier cycles and hold out 248 later cycles. Fit-cycle RMSE is 0.0563 V; later-cycle RMSE is 0.1916 V, MAE 0.1408 V, and p95 absolute error 0.4069 V. This experiment uses measured per-cycle capacity as reference SOC, so it is not an onboard estimate. It has no temperature time series, EV pack, BMS signals, or attack labels. It does not pass a deployment-accuracy criterion.
- Additional cell-held-out check: fit the same model using 150 earlier CS2_33 cycles and score all 775 cycles from independent CALCE cell CS2_34. The cross-cell RMSE is 0.0919 V, MAE 0.0691 V, and p95 absolute error 0.1761 V over 77,435 decimated samples. Both cells are one chemistry and one nominal 0.5C cycling profile, and the method still uses measured discharge capacity as reference SOC. This narrows cell-level evidence gaps but does not validate a pack, thermal model, detector, vehicle, or safety response; no deployment criterion exists. Details and archive hashes are in `docs/DATA_VALIDATION.md`.
- Public-cell validation is repeatable from checksum-pinned raw archives using `scripts/download_calce.py` (or `make download-calce`), then the single-cell and cross-cell validation scripts. Both downloaded archives matched their recorded SHA-256 hashes and extracted to 23 CS2_34 workbooks plus the CS2_33 source set. Raw archives remain untracked under the ignored `data/raw/` directory.
- Updated full held-out evaluation completed successfully on seeds 1000–1199 (200 runs per scenario; 1,400 total) with config hash `f56e499aeb4d481e` in 695.6 s. Updated baseline B3 false alarms: 0.160 episodes/hour, below the existing 0.20/hour target; B2 is 0.135/hour. B3 attack detection rates were AT1 98.5%, AT2 81.0%, AT3 98.5%, AT4 19.5%, AT5 98.5%, and AT6 15.5%. B3 is below B2 on AT2, AT3, AT4, and AT6 despite a slightly higher baseline alarm rate; AT4/AT6 remain substantial limitations. Paired hazard rates improved AT2 0.5%→0%, AT3 28%→0%, AT5 97%→0%; other scenarios had no hazards in either arm. Full metrics, CIs, delay and temperature/voltage outcomes: `data/results/results.json`, `data/results/tables.md`; run provenance: `data/results/meta.json`. The prior report files were preserved under `data/results/p7-pre-response-recovery/`. `/api/benchmarks` now serves the updated root report (HTTP 200; config hash and seeds verified).

## Current release blockers

1. **Residual alarm and detection performance.** The original guard-clamp false confirmation is fixed in the tested simulation: validation seeds 0–99 show 0.13 B3 episodes/hour, and held-out seeds 1000–1199 show 0.160/hour, both below the existing 0.20/hour target. In a separate direct pass over the same 200 held-out honest baseline seeds, 30 entered SUSPECT, 27 cleared after clean challenges, and none reached CONFIRMED or SAFE_MODE; three remained SUSPECT at end of run. The residual false-alarm experience still needs attention. B3's held-out false-alarm rate is slightly higher than B2's (0.135/hour), and B3 detection is lower than B2 for AT2, AT3, AT4, and AT6. This does not meet the SPEC sanity expectation that B3 should not be worse than B2 on telemetry attacks at equal false-alarm rate. AT4 B3 detects 19.5% and AT6 15.5%; these are limitations, not deployment-ready performance. State-count evidence: `data/results/p10_baseline_state_test.json`.
2. **Evaluation runtime.** The updated 1,400-run held-out evaluation took 695.6 seconds (11 min 35.6 s), improving on the earlier 1,802.4 s but still missing the planned <600-second gate. No thresholds were tuned on test seeds.
3. **Physical model evidence.** CALCE now provides a two-cell cell-held-out voltage check, but the within-cell later-cycle error remains high and there is still no pack test, thermal instrumentation, chemistry/temperature/aging coverage, vehicle drive/charge profile, or physical detector/response validation.
4. **Vehicle/BMS integration.** There is no Tesla or other OEM interface, CAN/UDS integration, approved signal map, vehicle credentials, hardware-in-the-loop rig, or real battery connection. Vehicle labels and car art are visual examples only.
5. **Safety response and emergency delivery.** SAFE_MODE, sensor substitution, safe-stop assist, force-send, and evidence capture are prototype simulations/local UI behaviors. There is no vehicle actuator, parking system, emergency-services connection, durable authenticated alert service, or guaranteed delivery without connectivity. Never present them to a driver as an operational safety feature.
6. **Production security.** The API has no production authentication, authorization, or TLS setup. Deterministic probe-key fallbacks support reproducible simulation only; secure hardware-backed provisioning/storage/rotation is absent. Do not expose the current API to a public network or connect it to a vehicle.
7. **Unfinished release verification.** No clean Git clone has been checked from a committed release snapshot; the current working tree has broad uncommitted changes and the seven static replay JSON files are untracked, so they must be included in the release snapshot. A fresh Chrome smoke confirmed the live dashboard loaded current benchmark data and an honest, no-injection run streamed normally at first, then entered SUSPECT by simulated 09:19; the driver preview correctly cautioned that this alert alone does not prove malware. The browser wait timed out before recovery could be checked, and there was no screenshot or console-error audit. Full browser incident recovery, accessibility, offline operation, and Playwright checks remain open. Python dependency audit did not complete because the vulnerability service stalled. The soak confirms all 21 sessions delivered 600 frames, but there is no RSS limit or memory acceptance threshold; release packaging drills remain open.

## Required path before any vehicle trial

1. Investigate why B3 detection falls below B2 on AT2, AT3, AT4, and AT6 using validation seeds only; preserve P3 attack definitions and do not tune against the test results. Any changed detector/response requires a new frozen configuration and a separately untouched test split.
2. Collect independently instrumented cell and pack data across units, chemistry, age, temperature, and operating profiles. Establish sensor calibration, ground truth, split by physical unit, and numerical pass criteria with battery and safety engineers.
3. Specify one target vehicle/BMS, authorized interface, signal ownership, read/write boundary, and OEM approval. Begin with passive read-only telemetry in replay/HIL; do not send actuator or parking commands.
4. Complete hazard analysis, functional-safety case, cybersecurity threat analysis, secure key lifecycle, authenticated/encrypted communications, audit retention, update/rollback plan, watchdog and communications-loss behavior, and human-factors review. Independently review every driver instruction and emergency behavior.
5. Validate in simulation, software HIL, hardware HIL, and a protected instrumented pack test facility with independent cutoffs and a qualified safety engineer. Test sensor failures, stale/replayed data, network loss, restarts, config faults, safe-stop failure, reset, and evidence integrity. Require signed acceptance and OEM/regulatory authorization before any closed-loop vehicle action.
6. Finish the release gate: clean committed checkout, fresh setup, all tests, security audits, 3× scenario soak with memory/error criteria, backend-kill/config/data failure drills, offline replay, supported browser walkthrough, selected UI accessibility checks, license decision, and user-reviewed release notes.

Relevant engineering/regulatory workstreams depend on vehicle category and jurisdiction: [UN Regulation No. 155](https://unece.org/transport/documents/2021/03/standards/un-regulation-no-155-cyber-security-and-cyber-security), [UN Regulation No. 156](https://unece.org/transport/documents/2021/03/standards/un-regulation-no-156-software-update-and-software-update), [ISO/SAE 21434](https://www.iso.org/standard/70918.html), and [ISO 26262](https://www.iso.org/standard/68384.html). Listing them does not imply this prototype conforms to them.
